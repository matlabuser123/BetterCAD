# P18-CLI-001 — adversarial review

```text
reviewer         an independent agent that was given the code, the attack list of the brief and the experiments it needed, and NOT my conclusions;
                 read-only on the repository; 121 tool calls; ~23 minutes
questions        the brief's 41 attack questions, grouped into 15 (a section below says which found nothing)
critical         0
findings         14 numbered, of which 11 required a change to the code, the tests or the gate (all made), and 3 are recorded and left (reason given)
production       2 defects in the CLI (a wrong startTime; an exit code that depended on the file), 1 trap (the --output default), 1 gap (an unbounded id)
credible gate    the ownership gate had 9 plausible escapes (all closed) and 4 contrived ones (3 closed, 1 recorded)
```

The reviewer's own words about its method: it hand-checked the physics through the real executable (a slab with 300 K and 400 K caps gives a gradient of 5000 K/m and |q| = 225000 W/m² along −z, Dirichlet reactions summing to 1e-11 W), mutated copies of the CLI source to see whether the gate or the tests noticed (with controls that were rejected, so the harness worked), and fed the executable 9 extreme variants of the plate and every id, path and argument shape it could think of.

## What the gate still cannot see (recorded, not hidden)

* **`ThermalOutput.hpp`'s required tokens can remain in dead code.** The header must still *contain* `std::isfinite`, `sawNonFinite_ = true`, `candidate.id < e.low.id`, `valueFinite` …; a determined author could keep them and bypass them. The unit tests that call `FiniteJson`, `validationJson` and `extremaOf` on hand-built inputs are what would notice (probes CO01, CO02, CR02, CR23 are each killed by a test).
* **A new header that is not a `Thermal*` file** (a shared `Commands.hpp`, `Cli.cpp`, `StructuredOutput.hpp`) is not scanned. Those are shared infrastructure that earlier milestones qualify, and the thermal verbs' registrations in `Cli.cpp` hold help text only. A thermal helper named otherwise would escape the glob.
* **Token assembly by means other than `##`/`#define`** (a constexpr string concatenation naming a function) is not a thing C++ can do to a *name*, so this is contrived.
* The gate is a structural defence. The behavioural defence is the equivalence tests and the mutation campaign, and the reviewer agreed that the arithmetic CLI code is limited to one `std::hypot` over a stored triple.

## The attack-list items for which the reviewer found nothing

The reviewer tried, and reports **no counterexample** for: Tet4, load/BC integration, Robin, a solver, backward Euler, `grad T` or `q` recovery and a CLI-side balance sum in any CLI file; a CLI-defined validation threshold or "solver success is success" (every exit-status site enumerated: always `run.accepted()` or a `failure()` return); a `NodeId`/`ElementId` used as an index; a raw mesh id, facet or DOF accepted as a target (no such option exists; `--node`/`--facet` are exit 2); a nearest-face rebind (an unresolved `face:Extrude001:side:9991` survived add → save → settings → solve and was refused as `loads_invalid`); a defaulted material, a steady analysis requiring ρ/cp, a transient requiring a prescribed temperature, a regularised singular model, an `abs()`-corrected load, a clamped `h`/`dt`/`T`; a partially rewritten file (ids 0, 05, `5 `, empty, `+5`, `-5`, unicode digits, `0x10`, `1e3`, 2^64−1; repeated options; `--`; empty values; `--opt=value`; a directory as the file; a read-only file; a missing file; a unicode path with spaces — the SHA-256 never moved); a read-only command changing bytes; non-strict stdout (all 7 commands, on the plate and on 9 extreme variants, parsed with an independent parser); payload and exit status disagreeing; the chain differing from `vztest::derive()` (checked call by call: same order, same arguments, same definition copy); a dangling pointer in a moved run (every stored type holds values); help claiming unsupported physics; a `batch` that is not all-or-nothing (except the dry-run id, finding 7); time handled as `index × dt`; a node/element count confusion.

## Observations outside the CLI (core), reported and not attributed or changed

* `relative_residual_tolerance` of 1e300 loads, and `thermal-validate`/`thermal-solve` then **accept** with status PASS: `validate(ThermalSolverSettings)` requires only "finite and positive" (`ThermalData.cpp`), so the acceptance threshold is user-editable canonical data with no upper bound. This is a P18-DATA/P18-VALID design question for the owner.
* A fine but valid time step (0.0001 s, 23 750 steps) is refused by the core with `balance_out_of_tolerance` at state 812.
* A prescribed or ambient temperature of exactly 0 K, and a denormal 1e-320 K, are accepted.
* In the shipped plate, `mesh-info` reports 81 nodes and 127 tetrahedra for global targets 0.5, 0.012, 0.006 and 0.002 m. This is the P16-SIZE-001 finding already on record (OCCT triangulates a planar face with two triangles whatever the global target; the hole's deflection governs the rest), and the workflow's local-size step was moved from a setting that changes nothing to one (`side:5` at 0.8 mm) that visibly does.
