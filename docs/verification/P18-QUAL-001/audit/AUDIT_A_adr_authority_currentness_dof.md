### Differences between the brief's labels and what the ADRs say
* **ADR-049** is NOT a "P16/one-solid limitation" ADR. It is the *scope* ADR: linear conduction, constant isotropic k (and constant rho, cp), Tet4, one scalar T per node, steady + backward-Euler transient, 2 load kinds, 2 BC kinds, long refusal list. The one-solid limit is one *constraint* inside it (ADR-049:39-42, "follows from P16 refusing a multi-solid body").
* **ADR-050** is the *layer-45* decision (thermal below structural so the thermo-mechanical coupling can flow down). Solver reuse appears only as a *consequence* it leaves open ("two admissible answers", ADR-050:82-108); the actual solver-reuse decision is **ADR-052** (extraction to `linalg`, layer 5). So "solver reuse/dependency-layer constraint" is split across ADR-050 (constraint) and ADR-052 (decision).
* ADR-051 = single validated boundary `requireThermalModel`; ADR-053 = acceptance in one place; ADR-054 = read-only VIZ; ADR-055 = commands/history intent only; ADR-056 = persistence intent only; ADR-057 = one production entry `runThermalAnalysis`, CLI is an adapter.

## A3. CURRENTNESS

### Dependency graph and what each link compares
```text
CAD feature (ObjectId body)  --P16-->  GeometryRevision (64-bit mix of logical dependency revisions; GeometryPreparation.hpp:97-103,174)
   -> P16 mesh: MeshStamp {MeshId (process-local atomic counter), generation} (MeshIds.hpp:178-188); Mesher::currency(document, control) is exact (sizing intent + geometry rev)
   -> ThermalModel (requireThermalModel, ThermalAnalysis.cpp:149): body, control, mesh*, map*, quality*, k (by value), geometryRevision   [snapshot, borrowed]
   -> ThermalDofMap {stamp, nodes}            describes(mesh) = Mesh::owns(stamp) && nodeCount     (ThermalDof.hpp:218; .cpp:107)
   -> PreparedThermalLoads / PreparedThermalBoundary {source: body, stamp, nodeCount, geometry, canonical list BY VALUE}
   -> ThermalSystem  (K, C, Q)       source = ThermalSystemSource {body, stamp, nodeCount, geometry, mode, materialId, materialRevision, loads[], convections[]}
   -> SteadyThermalSolution / TransientThermalSolution   source = {system source, prescribed-T conditions[], (initial, transient), settings}
   -> ThermalPostResult  / ThermalBalanceResult           source = ThermalPostSource {mode, system source, temps[], settings, initial?, transient?}   (Balance source IS ThermalPostSource, ThermalBalance.hpp:392)
   -> ThermalValidationReport    source = ThermalResultSource {body, control, geometry, mesh stamp, material id+revision, analysis id + analysisRevision, mode} + policyFingerprint
   -> VIZ ThermalDisplayState / ThermalResultView / cache keys  (no source of its own; recomputed from the above on every call)
```
Mechanism (all verified in code): each derived object stores its source as a **value** (no pointer, address, timestamp or hash of bytes: `ThermalAnalysisObject.hpp:134-137`, `ThermalLoadVector.hpp:244-247`), equality is `= default` so a new field cannot be added without being compared, and `staleReasons` names which field moved. `isCurrent(obj, document, model, ...)` recomputes the current source from the document NOW (material resolved afresh: `ThermalSystem.cpp:214-222`, `ThermalSolve.cpp:577`) and compares. Counts are used only as an ADDITIONAL guard (`nodeCount` next to the stamp, because "a stamp identifies the BUILDER not the snapshot", `ThermalDof.hpp:196-200`), never instead of identity.

## DEFECTS SUSPECTED
(Ranked. None is a demonstrated wrong number; D1 is a contradiction with the brief's rule, D2-D4 are design hazards.)

* **D1 (Medium, policy contradiction).** Two currentness regimes. Brief: "no numerical-equality resurrection (edit, result stale, undo/recreate equal values -> source-generation policy decides)". Code: only `ThermalResultSource`/`ThermalValidationReport` are generation-keyed (`ThermalAnalysisObject.hpp:158`, `ThermalValidation.cpp:1676`). Prepared loads/boundary, system, solutions, POST and BALANCE are keyed on canonical-intent VALUES with `==` on doubles and carry NO analysis id/revision (`ThermalLoadVector.hpp:268`, `ThermalBoundary.hpp:331`, `ThermalSystem.hpp:217`, `ThermalSolve.hpp:385`, `ThermalTransient.hpp:390`, `ThermalPost.hpp:290`). Consequences, all reproducible from the existing tests: (a) undo/redo of an edit revives the old POST/BALANCE as Current while the validation report stays Stale (`ThermalCommand_UndoCurrentnessFollowsSourceIdentity`) - VIZ shows a current result with a stale badge (ADR-055:73-75 admits it); (b) a manual edit-back (no undo) revives the chain the same way, not pinned by any test; (c) results of analysis A are "current" for a different analysis B with an equal definition on the same mesh and material (no analysis identity in the chain sources); (d) the code comment at `tests/thermal/ThermalValidationMappedTests.cpp:1081-1082` says currentness "is identity, not 'the same values again'", which describes the report only. Soundness is real (a fresh solve gives the same bits; asserted), so this is an owner decision about the stated rule, not a numerical defect.
* **D2 (Low/Med, dead parallel API).** `ThermalResult::create`, `ResultCurrency`, `resultCurrency`, `analysisState`, `ThermalResultSlot` (`ThermalResult.hpp:80,160,194,237,263`) have no production caller (grep of `src/`, `apps/`: only `ThermalResult.cpp` itself; the validator uses only `currentResultSource` + `staleReasons`). The header (`:20-23`) claims they are "the only currentness answers in P18", which is false: the live answers are the per-object `isCurrent`, `thermal::isCurrent(report)` and `ThermalDisplayState`. ~20 tests (`ThermalData_*`, e.g. `..._FailedAttemptIsNotCurrent`, `..._TheStateMachineReachesEveryStateItDeclares`) therefore assure a code path the product does not take. Also `ThermalResult::describes` compares the stamp only (no node count), unlike every other describes (`ThermalResult.cpp:140-143`).
* **D3 (Low, hazard).** `ThermalModel` borrows `Mesher` storage (`ThermalAnalysis.hpp:143-148,212-214`) and every `isCurrent(..., model, ...)` trusts the model's own snapshot (`geometryRevision`, mesh stamp). A model held across a remesh or geometry edit makes old derived objects read Current (or dangles). The test suite works around it by hand (`ThermalAssemblyMappedTests.cpp:590-592`). In-tree production paths rebuild the model every call (`ThermalAnalysisRun.cpp:68`, `ThermalValidation.cpp:1353`, `ThermalInspection.cpp:154`), so unreachable today; no guard, no test (51.15).
* **D4 (Low).** Mesh identity = `MeshStamp` + node count only (`ThermalDof.hpp:196-200`; all `describes`). Two snapshots of one `MeshBuilder` with equal node count but different elements are indistinguishable. Reachable only with hand-built meshes (the Mesher always issues fresh stamps); `ThermalAssembly_SameBuilderLaterSnapshotIsNotTheSameMesh` covers the node-count variant only.
* **D5 (Low, documentation drift).** ADR-049:187 (one TU), ADR-052 verification names (`architecture.targets.thermal-link-graph`, `.linalg-link-graph` do not exist), ADR-057:64 ("17 rules, 73 fixtures" vs 21 rules / 102 fixtures). The brief's one-line labels for ADR-049/050 differ from the ADRs (see top of A1).
* **D6 (Low).** Architecture gates are regex scans on text with `//[^\n]*` removed (e.g. `CheckValidationOwnership.cmake:55`, `CheckThermalVizOwnership.cmake:53`): a `"//"` inside a string literal hides the rest of that line; `/* */` comments are not stripped. A banned token can be hidden after a string containing `//`. Theoretical, but these gates are the sole enforcement for ADR-053/054/055/056/057 ownership.
* **D7 (Info, open owner decisions already recorded).** JSON repeated key = last wins for all object types (`ThermalPersistence_ARepeatedKeyInTheFileIsLastWinsAsEverywhereInTheFormat`); data-model `validate` accepts `FaceName{}` (commands/file refuse it); `final_only` multi-step transient cannot be fully accepted (`ThermalValidation_AFinalOnlyHistoryOfSeveralStepsCannotBeFullyAccepted`).
* **D8 (Low).** Temperature is one type for absolute T and for differences (`Units.hpp:162-164`); the `>= 0 K` rule is runtime-only (`ThermalData.hpp:95`). A negative temperature DIFFERENCE passed where an absolute T is validated is refused; the reverse (an absolute T used as a difference) is not type-detectable.
* **D9 (Low).** `ThermalValidationReport` is a plain aggregate with public mutable `checks`/`findings` (`ThermalValidation.hpp:488-505`); ADR-053 clauses 2-3 hold for derived accessors and const views (compile-fail tests use const views) but a holder of a non-const report can rewrite findings. `accepted()` ignores report currency by design (`:565`); consumers must also call `isCurrent(report, ...)`.
* **D10 (Low).** Numeric constants scattered by design but duplicated once: `kSymmetryTolerance = 1e-13` (`ThermalSystem.cpp:47`) and `kEffectiveSymmetryTolerance = 1e-13` (`ThermalTransient.cpp:38`); others: `kAnchorTolerance 1e-10` (`ThermalSolve.hpp:272`), `kBalance*` (`ThermalBalance.hpp:150-154`), `kTimeGridTolerance 1e-9` (`ThermalTransient.hpp:170`), `kDegeneracyNoiseFactor 16` (`ThermalElement.cpp:149`), validation thresholds (`ThermalValidation.hpp:94-109`).
* **D11 (Low).** Not gated: "thermal links no Eigen target" (ADR-052 comment only), "no Qt/OCCT in thermal viz files" (ADR-054.1), "thermal must not hold a second sparse kernel" (ADR-050/052).
