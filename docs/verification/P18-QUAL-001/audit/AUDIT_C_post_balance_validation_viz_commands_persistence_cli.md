## CONSOLIDATED: DEFECTS SUSPECTED (ranked by risk to qualification; none is a proven wrong number)

1. D-A (persistence, medium). The writer can emit a file the reader refuses (C56 D1/D2). A definition whose FaceName has an invalid feature handle (data-model `validate` admits it, commands and the reader refuse it, ThermalCommands.cpp:61-75 vs src/io/json/ThermalAnalysisJson.cpp:148-159, writer :491-546) saves successfully and then fails to load; likewise ids above 2^53-1 in GeometryReference sub-fields (DatumJson.cpp:212-238 writes, JsonReader.cpp:144-153 caps). The code's own rule at ThermalAnalysisJson.cpp:499 says the writer must not emit what the reader refuses. No test covers the write-then-read direction. Reachable only through the data-model API (ThermalAnalysis::create/setDefinition), not through commands or the CLI.
2. D-B (viewer, medium, design). Nothing in production enforces "a stale result is not drawn as current". `ThermalContourCache::colours`, `heatFluxVectorGlyphs` and `ThermalResultView::of` accept any result that matches the mesh and numbering; staleness is a separate `ThermalDisplayState` that the caller must consult, and the only test that suppresses the contour does so by hand (ThermalViz_StaleResultSuppressesTheContourAndMarksTheMeshStale). `inspectThermalNode/Element` default `resultState = Current` (ThermalInspection.hpp:214,219), so an omitted argument mislabels a stale inspection. Same-size remesh is refused correctly by every path that was tested.
3. D-C (viewer, medium, design). `Viewer::displayOverlay` (OcctViewer.cpp:434-445) ignores `ThermalOverlay::incompleteTargets`; a mixed overlay (one Complete glyph, one ZeroClassified) is drawn as whole. The cardinality classifier itself is fully tested as a pure function, but no test makes the real builders see classified != expected, and the real-pipeline test would still pass if `classified` were wired to the render-triangle count.
4. D-D (policy/usability, medium). The default `TransientSettings::output` is `FinalOnly` (ThermalData.hpp:341) and BALANCE refuses a multi-step FinalOnly history (ThermalBalance.cpp:644-659), so a transient analysis with default settings and more than one step can never be ACCEPTED (TV_BALANCE fails with BalanceMissing; ThermalValidation_AFinalOnlyHistoryOfSeveralStepsCannotBeFullyAccepted). This is deliberate and explained in the finding text, but it means every accepted transient requires an explicit EveryStep, and the history (and file-independent memory) then grows with step count.
5. D-E (acceptance coherence, low-medium). The solver residual gate is 1e-9 (ThermalData.hpp:307) while the balance gate is |B| <= 1e-12 W + 1e-13 (gross + arithmetic) (ThermalBalance.hpp:150-151), four orders tighter. The balance residual is the sum of the free-row residuals, so a solve that is inside the solver gate but at, say, 1e-11 relative would be accepted by V10 and refused by V13. In practice the direct solver delivers about 1e-16 and the tolerance is "measured" on qualified references, but no test drives a solve on an element at the mesh acceptance bounds (3r/R = 7.0e-6, aspect 700) through BALANCE (ThermalValidationLawTests.cpp has no balance reference; line 331 uses only the solve residual). Possible false rejections near the mesh bounds, undetected.
6. D-F (validation, low). `classifyThermalMesh` silently skips a classifiable metric whose P16 summary is absent or has count 0 (ThermalValidation.cpp:516-518) and never compares `summary.count` with `quality.tetCount`. P16 makes this unreachable today (`evaluateMeshQuality` always summarises, structural failure gives Invalid), but the validator does not defend the invariant, so a P16 regression would pass a mesh with an unjudged metric. Unit-tested only for NaN summaries and invalidElements.
7. D-G (CLI, low). `PASS_WITH_WARNINGS` exits 0 through the CLI is never exercised: ThermalCli_WarningOnlyReportExitsZeroAndKeepsTheWarning drives an INFO finding (`transient_without_datum`, asserted "info" at ThermalCliTests.cpp:1275), status PASS. No CLI test contains a warning-severity finding. Protected only by the pinned exit statement (arch rule 12) and the core tests.
8. D-H (CLI/harness, low). The "fresh-binary proof" (ThermalWorkflow.cmake:42-117; ThermalReferenceWorkflow.cmake:46-93) records absolute path, size, SHA-256 and runtime-library resolution and fails on relative/foreign/unresolved binaries, but nothing compares the hash to an expected value, nothing is time-compared with sources, and `version` output is not asserted, so a stale-but-self-consistent build tree passes. The header concedes freshness is the harness's clean rebuild.
9. D-I (arch gate, low). CheckThermalCliOwnership rule 13 (no arithmetic on `.si()`) is bypassable by compound assignment (`total += x.si()`), by raw-double accessor arithmetic (`pivotRatio() / 2`), and by `std::accumulate`-style algorithms; thermal logic placed in a non-`Thermal*`-named CLI file is scanned by no CLI rule (only by name-based Recovery/Balance/Validation rules). Current CLI code is clean (hypot of a stored triple at ThermalReports.cpp:255-257 is benign).
10. D-J (dead code, info). `ThermalResult`/`ThermalResultSlot` (P18-DATA-001, src/thermal/ThermalResult.cpp:44-136, including its finiteness gate) are not used by the production chain (ThermalAnalysisRun.cpp builds SteadyThermalSolution + ThermalPostResult + ThermalBalanceResult); they are exercised only by ThermalDataTests and friends. Their finiteness/cardinality checks protect nothing at runtime; acceptance of finiteness is in POST + TV_RESULT_FINITE/TV_POST.
11. D-K (semantics, info). Transient balance uses the RESOLVED initial state (prescribed unknowns already replaced, ThermalTransient.hpp:336-340), so the heat implicitly injected at t=0 by a prescription that differs from the user's initial temperature is not in the balance; it is reported only as INFO InitialConditionOverriddenByPrescription (documented policy, ThermalTransient.hpp:339, ThermalValidation.hpp:301).
12. D-L (validation, info/design). TV_POST verifies finiteness, cardinality and bitwise temperature equality but not that q = -k grad T of the presented arrays (ThermalValidation.cpp:818-886); a finite but wrong q of matching provenance passes TV_POST. Protection is the private constructor of ThermalPostResult plus source equality (ThermalValidation_RejectsSameIdsNewMeshSource).
13. Minor items from sub-auditors: viewer non-finite stored flux is counted as "skipped" like a zero flux instead of being refused (ThermalOverlay.cpp:258,377); `ThermalInspection.cpp:126` shows a Pass badge with no result held; writer treats -0.0 == +0.0 as a no-op edit (documented, tested); duplicate id-cap constant `kLargestFileId` in ThermalEdits.cpp:119 vs io `kMaxFileId`; CheckTargetDependencies rules 2 and 3 have no negative fixture; stale comment "five cases" at ThermalReferenceWorkflow.cmake:342 (regex expects 6); `thermal-validate/balance` rejected runs print the payload, exit 1 and leave stderr empty.

## DEFECTS SUSPECTED

D1 (medium, design). No production code enforces "stale is not drawn as current". `ThermalContourCache::colours` (ThermalContour.hpp:188), `heatFluxVectorGlyphs`, `ResultView::of` accept any result that matches the mesh/numbering, even if the material or loads moved. `inspectThermalNode/Element` default `resultState = ThermalResultState::Current` (ThermalInspection.hpp:214, 219), so omitting the argument mislabels a stale inspection. The only enforcement is the caller consulting `thermalFieldAvailability`. Mitigated by tests of the protocol, not by the API.

D2 (medium, design). `Viewer::displayOverlay(ThermalOverlay)` (OcctViewer.cpp:434-445) refuses only invalid id or empty segments. `ThermalOverlay::incompleteTargets` (ThermalOverlay.hpp:115) is never examined at the boundary where geometry reaches the screen. A mixed overlay with some Partial/ZeroClassified glyphs displays as if whole. Overlay presentations have no stale or incomplete marker.

D3 (low). ThermalOverlay.cpp:258 `if (m > 0.0 && std::isfinite(m))` otherwise `hasDirection=false`, so a NaN/Inf stored magnitude counts into `skipped` ("zero flux, no direction"). Same at ThermalOverlay.cpp:377 for a non-finite applied flux (`hasDirection = isfinite && != 0`). A non-finite value is hidden under the "no arrow because zero" bucket instead of being refused (the field channel path does refuse). POST should never emit one, so the risk is only against a corrupt result.

D4 (low). ThermalInspection.cpp:126: `otherResult` is false when `post == nullptr`, so a current report's Pass badge is shown with no result held (e.g. after a failed re-solve with no old result). Possibly intended, but the badge can then sit beside a "NO RESULT" banner.

D5 (low). Arch check blind spots (CheckThermalVizOwnership.cmake): name-based physics list (:36) misses inline arithmetic; stale-flag regex (:41) matches only `bool [is]Stale... ;={,)`, so it will not flag `bool stale() const` or `Viewer::setMeshStale`-style setters in apps; rules do not scan `src/renderer/occt/` (the actual metre-to-millimetre site) or forbid `displayDeformedMesh` anywhere. `K/mm` strings are not scanned.

D6 (info). `ThermalViz_StaleResult*` and the unit tests are [frame] (GPU). If the qualification environment filters `[frame]`, C4.3 and C4.7b lose their only on-screen evidence. No filter was found in CMake files, but the CI/preset config was not inspected.

D7 (info). Manual display range clamps out-of-range finite values to the end colour with no on-screen marker (ThermalContour.cpp:95-97); extreme manual spans (|min|,|max| near 1.8e308) overflow `span` to inf (ThermalContour.cpp:160) and degenerate to a clamped partition; not reachable from physical (non-negative, modest) fields.

## DEFECTS SUSPECTED

1. D1 (writer emits a file the reader refuses, FaceName with invalid feature handle). `validate(ThermalLoad/BoundaryCondition)` lets `FaceName{}` (invalid ObjectId) through; the commands add their own refusal (CPP:61-75), and the reader refuses it (JSON:148-159, comments JSON:140-147 and CPP:61-65 both state the data model accepts it). The writer has no equivalent check (JSON:491-546; only id-cap checks at 503-524). A definition built through `ThermalAnalysis::create(...)` or `setDefinition` directly (API, not commands; ARCH-CMD rule 8 only scans apps/, src/, renderer headers, not the data-model public API) saves successfully and then fails to load. The code itself says "THE WRITER MUST NOT EMIT WHAT THE READER REFUSES" (JSON:499). No test: FILE `ThermalPersistence_DanglingTargetsAreIntentAndAnInvalidFeatureHandleIsNot` only tests the read direction.
2. D2 (same class: id cap not applied to GeometryReference ids). Writer cap check covers only mesh, load id, BC id (JSON:512-524). `faceSelectorToJson` writes feature, entity, along, along_sketch, chamfer_edge and copy.feature/instance with `.value()` (DatumJson.cpp:212-238, 295), while `readId` caps at 2^53-1 (JR:144-153) and `readOptionalCount` caps edge and instance at 2^32-1 (DatumJson.cpp:155-168). `validate(FaceSelector)` has no range check (References.cpp:67-97), and the command layer accepts any valid handle. Result: a model-valid FaceName with an id above the cap saves but never loads. Practically unreachable via sequential allocators; likely format-wide. No test.
3. D3 (hidden-member blind spot, see C5.1/C5.5): nothing detects a non-typed derived member added to a command class.
4. D4 (nuance, low): equality treats -0.0 == +0.0 (OBJ:138), so a no-op edit leaves the old zero bits (tested and intended, CMD `..ASignedZeroEditIsANoOp...`). Consequence: two histories reaching `==` definitions can write different bytes if a zero's sign differs (add -0.0 directly vs add +0.0 then "edit" to -0.0). The byte-identity-through-history test (`..SerializationIsByteIdenticalRepeatedlyAndIndependentOfHowItWasBuilt`) uses no zero. Harmless physically.
5. D5 (info): `ThermalPersistence_ACorruptFileLeavesTheOpenDocumentAlone` and the locale test (`..TheDecimalPointDoesNotDependOnTheLocale`) can pass without exercising their claim (by construction / locale not installed).
6. Doubles: no defect. Writer uses nlohmann 3.12.0 `dump(2)` (JR:37) = Grisu2 shortest-round-trip, `-0.0` kept, locale decimal point normalised (serializer.hpp:853-856); reader uses the library's strtod; FILE `..ExtremeAndAwkwardFiniteValuesSurviveBitForBit` verifies subnormal, DBL_MAX, 0.1+0.2, -0.0 and 1e-300 bit for bit. Command layer formats doubles only into `description()` (CPP:428-484), never parses them back (ARCH-CMD rule 5).
7. Command atomicity, code review result: no partial-mutation path found. execute: copy -> edit() on copy -> stage -> apply -> unstage on failure (CPP:179-194); apply = `modifyObject` which validates before assigning (OBJ:134-146); undo/redo check `definition == after_/before_` first (CPP:216,236) and then use the same validated apply; CommandHistory records and clears redo only after success (HIST:30-34) and keeps the command on its stack if undo/redo fails (HIST:48-50,63-65); Create: all checks precede `Document::addObject`, which itself allocates the id only after name checks (Document.cpp:503-509), so a failed create burns no id. One design note, not a defect: a no-op edit succeeds, is recorded and clears redo (HIST:33-34), consistent with P15-P17.
