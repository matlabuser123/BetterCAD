THIS IS A RESOURCE PARAMETER, NOT A GATE. ninja compiles the same
sources with the same flags and the same -Werror at any -j, runs the
same tests, and ctest's own -j 8 lives in qualify.cmd. Nothing about
what is built, or what has to pass, has been relaxed. The one real
cost is wall-clock: the measured 692-object debug build took about
8.4 min at a bound of 6, against P19-GEOM-001's 8m55s for a full
build at 16, so the penalty here is small.

WHY 4 AND NOT 6. Both were measured. The compile phase is what the
bound controls, and the two phases separate cleanly:

    compiles at 6   71.3 + 6 x 1.81 = 82.2 GB peak -> 0.4 GB headroom
    compiles at 4   71.3 + 4 x 1.81 = 78.5 GB peak -> about 4.3 GB
    the LINK        81.4 GB peak regardless of -j  -> 1.4 GB headroom

A bound of 6 does complete -- it was run end to end, 692/692 objects,
link included, no FAILED lines -- but it leaves 0.4 GB, and the
desktop session's pressure can rise during a multi-hour run. 4 buys
about 3.7 GB for a small time cost.

THE LIMIT OF THIS FIX, STATED PLAINLY. The link of the 1.40 GB debug
test executable needs 10.3 GB of commit in ONE process, so no job
bound protects it. It fits today with 1.4 GB to spare, measured, and
that margin is not large. If the interactive session's memory
pressure rises materially during attempt 2, the link can still fail,
and it would fail the same silent way. That is a property of this
machine under this load, not of the tree, and it is recorded here
rather than discovered again later.

NOT DONE, AND WHY: closing the user's applications to free commit is
not mine to do, and enlarging the page file is a system setting. The
commit limit did grow on its own under pressure, 80.8 -> 82.8 GB,
which is where the present margin comes from.
